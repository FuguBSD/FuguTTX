# FuguTTX — Project Specification

## TL;DR
- **FuguTTX produces TTX 1**, a small language model fine-tuned on OpenBSD knowledge that runs locally and offline on OpenBSD machines as a task-performing agent. The recipe: fine-tune **Qwen3-4B (Apache 2.0)** with **QLoRA continued pretraining plus agentic SFT** on a single **Scaleway H100 PCIe instance (starting at €2.73/hour)**, quantize to **GGUF Q4_K_M**, and run it CPU-only via the OpenBSD `misc/llama.cpp` port inside 16 GB RAM.
- **One language per concern, chosen to match OpenBSD culture.** Python (uv workspace) for everything model-side — data, synthesis, training, evaluation, quantization. Perl for the on-OpenBSD harness, written against base alone (zero CPAN dependencies) and sandboxed with pledge/unveil, doas, and dry-run gates. All Scaleway infrastructure is declared in **OpenTofu**; nothing is created by hand in the console, and GPU instances exist only for the duration of a training run.
- **The full compute budget for TTX 1 is modest — on the order of €200–500 of Scaleway GPU time** for the complete CPT+SFT program. The dominant risks are small-model hallucination on destructive commands, corpus staleness versus `-current`, and the absence of any published OpenBSD-specific CPU inference benchmark (FuguTTX measures and publishes one first-hand).

## Key Decisions

1. **Base model: Qwen3-4B (Apache 2.0).** It is the only current family that combines Apache-2.0 licensing, strong tool-calling/agentic ability, good C/Perl code capability, long context, and full fine-tuning-ecosystem support. Llama 3.x (its 700M-monthly-active-user clause plus naming/derivative restrictions) and Gemma 3 (Prohibited Use Policy plus flow-down redistribution obligations) carry non-OSI custom licenses that clash with OpenBSD's permissive-only culture and are excluded.
2. **Inference: the `misc/llama.cpp` port, CPU-only.** The port is actively maintained and builds across twelve architectures including amd64, aarch64, riscv64, and sparc64. There is **no CUDA/ROCm on OpenBSD**, so inference is CPU-only. A 4B model at Q4_K_M fits comfortably in 16 GB RAM.
3. **Training: Axolotl QLoRA on a Scaleway H100-1-80G, fully managed as infrastructure as code.** OpenTofu declares every cloud resource; the GPU instance is created at the start of a training session and destroyed at the end. Object storage is the only durable layer. Costs stay low because QLoRA runs finish in hours and per-minute billing plus disciplined `tofu destroy` bounds exposure.
4. **Method: continued pretraining, then supervised fine-tuning.** CPT on the OpenBSD domain corpus injects vocabulary and idioms; SFT on synthetic agentic traces (pf.conf debugging, pkg_add workflows, sysctl tuning) teaches tool use. Replay data and a low learning rate guard against catastrophic forgetting. Traces are generated by a Qwen3-32B teacher and hard-filtered before use.
5. **Variants are personas, and they earn their release.** TTX 1 serves the operator (sysadmin); candidate variants — Port and Code — serve the contributor, built as SFT overlays on TTX 1's CPT checkpoint rather than as separate bases. A variant ships only when evaluation shows the generalist fails its persona's suite and the overlay clears it; forking a variant to a different base model is an escalation, never the default.
6. **The corpus has two lanes, and the lane rule is absolute.** OpenBSD source (ISC/BSD), man pages (mandoc, ISC), and the FAQ/website (BSD-licensed, the `www` repo) form the redistributable-clean corpus that trains the model. Mailing-list archives and undeadly.org are copyright their individual authors — undeadly.org's footer reads verbatim: *"Articles and comments are copyright their respective authors, submission implies license to publish on this web site."* That material is used for evaluation and optional local RAG only; it never enters training data and its raw text is never redistributed.
7. **Languages and tools are fixed: Python for all model work, Perl for the harness, OpenTofu for infrastructure, `just` as the task runner.** Python never ships to the OpenBSD target; the harness never depends on anything outside base.
8. **The project is built to be developed autonomously by Claude agents.** Every pipeline stage has a deterministic entrypoint, every outcome a machine-checkable definition of done, and every credential a minimal scope — so agents can plan, implement, train, and evaluate end-to-end, with humans holding a short list of decisions: merges, release signing, licensing lanes, and spend beyond budget.

## Details

### 1. Project overview, goals, non-goals

**FuguTTX** is a project to produce **TTX 1**, a small language model fine-tuned on OpenBSD knowledge that runs locally and offline on OpenBSD machines as a task-performing agent — the **TTX agent**, model plus harness (see Terminology below). The name references tetrodotoxin (TTX), the toxin of the fugu pufferfish — apt for a project centered on OpenBSD, whose mascot is a pufferfish. The first release is **TTX 1**, the general OpenBSD sysadmin model; specialist variants are candidates promoted by evaluation evidence, not up-front commitments (§5).

**Goals:**
- Runs locally on OpenBSD with **≤16 GB RAM**, CPU-only, inside an open-source harness.
- Performs routine tasks: system configuration, maintenance, ports/package installation, `pf` debugging and configuration, `sysctl` tuning, and similar.
- Permissively licensed end-to-end (weights, harness, and — where possible — data), matching OpenBSD's ISC/BSD ethos.
- Reproducible end-to-end: every pipeline stage runs from a single `just` recipe, and every cloud resource is declared in OpenTofu.

**Non-goals:**
- No GPU inference on OpenBSD (no CUDA/ROCm exists there).
- Not a general chatbot; scope is OpenBSD sysadmin/dev tasks.
- No unattended execution of destructive commands without an explicit confirmation/dry-run gate.
- No Python on the production OpenBSD target.
- No hand-managed cloud resources — if it is not in OpenTofu, it does not exist.

**Terminology.** "Agent" is an overloaded word; this document uses five distinct terms and does not substitute one for another:

| Term | Meaning |
|---|---|
| **TTX model** | The fine-tuned weights (TTX 1, a Qwen3-4B derivative), distributed as GGUF. A model only ever proposes text and tool calls; it executes nothing. |
| **Harness** (`ttx`) | The Perl program (§9) that drives the tool loop, executes commands, and enforces every safety gate. The only component that touches the system. |
| **TTX agent** | Model plus harness running together on an OpenBSD machine — the product users interact with. "Agentic" (traces, evals, tool calls) always describes this system's behavior. |
| **Teacher/judge model** | Qwen3-32B served by vLLM on the training instance. Generates synthetic traces (teacher) and grades evaluations (judge). It never ships, never executes tools, and never touches a system. |
| **Development agents** | Claude agents that autonomously build and maintain this repository (§11). Part of the project's process, not its product; they never appear on the OpenBSD target. |

### 2. Tooling and language decisions

One language per concern, with the boundary drawn where the code runs:

| Concern | Decision | Rationale |

| Infrastructure as code | OpenTofu with the Scaleway provider | Open-source IaC matching the project's licensing ethos; makes the ephemeral-GPU lifecycle safe and repeatable |
| Task runner | `just` | One polyglot entrypoint across Python, Perl, and OpenTofu |

| Teacher/judge model | Qwen3-32B (Apache 2.0) served by vLLM on the H100 | Clean license provenance for synthetic data; one deployment doubles as trace generator and eval judge |
| CI | GitHub Actions | The corpus mirrors and the repo live on GitHub; CI stays lint/test/validate-only, with no cloud credentials |

### 3. Data / corpus plan

| Source | Format / access | Licensing | Extraction method |
|---|---|---|---|
| Man pages | mdoc/man macros; `man.openbsd.org`; in `src`/`ports` trees | ISC (mandoc) / per-file BSD-ISC | Render with `mandoc -T markdown`/`-T ascii` from the source tree |
| FAQ + website | HTML; `www` repo | BSD-licensed | Clone `www.git`, strip HTML → text |
| Base source (C) | C; `src` git mirror | ISC/BSD (ISC template preferred for new code) | Clone git mirror; walk tree |
| Ports infrastructure (Perl) | Perl + Makefiles; `ports` git mirror | BSD/ISC | Clone `ports.git` |
| Commit logs | git log from mirrors | Metadata; messages by committers | `git log` extraction |
| Mailing lists (misc/tech/ports/bugs) | mbox/HTML via marc.info, mail-archive.com | **Copyright respective authors** | Scrape for the eval/RAG corpus only; never enters training data |
| undeadly.org articles | HTML | **Copyright respective authors** | Scrape for the eval/RAG corpus only; never enters training data |

**Mirrors:** fetch from the official read-only git conversions at `github.com/openbsd/{src,ports,www,xenocara}`. The Game of Trees Hub mirror (`ssh://anonymous@openbsd.gothub.org/{src,ports,www,xenocara}.git`, at most one commit behind CVS) is the documented fallback. Direct CVS pulls are avoided as brittle.

**Pipeline stages:** (1) fetch/sync mirrors; (2) extract & normalize (mandoc render, HTML→text, code de-duplication); (3) clean & chunk (license-header stripping, near-dedup); (4) tag every chunk by source and license class; (5) emit **two** corpora — the **redistributable-clean corpus** (source, man, FAQ, www) used for CPT and shippable inside the weights, and the **eval/RAG corpus** (mailing lists, undeadly.org) used for evaluation and optional local retrieval. The license tag is machine-checked: nothing tagged eval/RAG can reach a training manifest.

### 4. Base model

**TTX 1 trains from Qwen3-4B (Apache 2.0).**
- **License:** Apache 2.0 across the whole dense family (0.6B/1.7B/4B/8B/14B/32B) — the single most important criterion given OpenBSD's insistence on permissive licensing. Llama and Gemma are disqualified on license grounds.
- **Capability at size:** Qwen3-4B rivals much larger prior-generation models, and the Qwen3 line has explicit agentic/tool-calling training. 4B fits CPU-only in 16 GB with room to spare for context.
- **Context:** Qwen3 dense models support 32K context at 0.6B–4B and 128K at 8B and above — ample for sysadmin tasks with retrieved man-page context.
- **Ecosystem:** first-class support in Axolotl, HF TRL, llama.cpp.

**Escalation rule:** if TTX 1 misses the Phase 4 agentic eval bar after reasonable iteration on data and hyperparameters, the base moves to **Qwen3-8B** (same license, 128K context, roughly half the CPU tokens/sec). The pipeline is size-agnostic; only configs change.

**Thinking mode:** Qwen3's toggleable thinking mode stays **off** for TTX 1. At CPU token rates, long reasoning chains destroy interactive latency; SFT traces therefore contain no thinking blocks, and the harness requests non-thinking completions.

**Variant bases:** specialist variants share this base and its CPT checkpoint by default; the escalation policy for moving a variant to a different base lives in §5.

**Bench:** IBM Granite 3.x and SmolLM3-3B (both Apache 2.0) are the named fallbacks should the Qwen line become unavailable or unsuitable; SmolLM3's fully open weights+data+recipe would suit a "fully open" TTX variant.

### 5. Variants

TTX releases are organized around **user personas, not data slices**. TTX 1 serves the **operator**: the sysadmin who configures, maintains, and debugs an OpenBSD system. Candidate variants serve the **contributor**: the developer who writes ports and patches. The boundary is sharp — *using* packages (`pkg_add`, `pkg_delete`, `pkg_info`) is operator work and stays in TTX 1; *creating and updating* ports is contributor work and belongs to a variant.

**Variants are SFT overlays, not forks.** Every variant starts from TTX 1's CPT checkpoint: the redistributable-clean corpus already contains the base source tree and the ports tree, so the domain knowledge is shared, and what distinguishes a variant is its SFT trace mix, expressed as a per-variant Axolotl overlay in `packages/ttx-train/configs/`. That keeps one base model, one CPT run, and one validated inference envelope across the whole family. Moving a variant to a different base model is an **escalation, never the default**: it is taken only when the overlay demonstrably misses the variant's eval bar, and the replacement base must satisfy the same criteria that selected the §4 base — permissive license (Apache 2.0 or equivalent), CPU-only fit in ≤16 GB at Q4_K_M, credible tool-calling, C and Perl code capability, and first-class Axolotl/llama.cpp support. (At the time of writing, **Qwen2.5-Coder-7B** — Apache 2.0, continue-pretrained across 92 programming languages including C and Perl — is the strongest such candidate for a code-focused fork; its 3B sibling carries the restrictive Qwen-Research license and is excluded.)

**Promotion rule.** A variant is a candidate until evaluation earns it a release. Three conditions, all checked against versioned eval suites (§12), must hold:
1. The persona has its own eval suite, built and maintained like every other eval asset.
2. TTX 1 measurably fails that suite.
3. The variant measurably clears it, without regressing on the general suite.

If a candidate fails condition 2, the generalist already covers the persona and no variant ships — that is a success, not a failure.

**Candidate variants:**

| Candidate | Persona / scope | Eval story |
|---|---|---|
| **TTX 1 Port** | Ports-tree maintenance: Makefiles, `bsd.port.mk`, PLIST discipline, updating ports to new upstream releases | Strongest of the candidates: a port builds or it does not; `portcheck` and `make port-lib-depends-check` are machine-checkable; "update port X to upstream release Y" grades end-to-end in a qemu VM |
| **TTX 1 Code** | OpenBSD-flavored development: patches against the ports and src trees, Perl, shell, `rc.d` scripts | Weakest of the candidates: no established benchmark exists for OpenBSD src work, so the suite must be built (does the patch apply, compile, pass regress?). Ambitious kernel/libc patch generation is out of scope for this size class |

The two candidates overlap where code meets the ports tree. If their eval suites show substantial overlap, they merge into a single contributor variant rather than shipping as two models a user must choose between — on a 16 GB machine, every additional GGUF is real friction.

**Naming.** Variants inherit the release version: TTX 1 Port is the Port overlay of TTX 1, and a retrained family ships together as TTX 2, TTX 2 Port, and so on.

### 6. Training plan on Scaleway

**Instances (Paris PAR-2 / Warsaw WAW-2; on-demand, per-minute billing, prices before tax):**

| Instance | GPUs | GPU VRAM | System RAM | €/hour |
|---|---|---|---|---|
| H100-1-80G | 1× H100 PCIe | 80 GB | 240 GB | €2.73 ("starting at") |
| L40S-1-48G | 1× L40S | 48 GB | 96 GB | €1.47 ("starting at") |

Extra billed items: Block Storage (root volume), Flexible IP (€0.004/hour), Object Storage. Scratch NVMe on these instances is ephemeral and disappears at instance deletion — by design, nothing durable lives on the instance.

**Instance selection:** the **H100-1-80G is the standard training instance**, declared as the default in the OpenTofu train stack. 80 GB holds a 4B/8B model plus QLoRA optimizer state at long context with enormous headroom (public reference points: an 8B QLoRA over 2 epochs completes in roughly 3–6 hours on a single high-end GPU; 7B QLoRA peaks under 8 GiB VRAM). The **L40S-1-48G** is exposed as an `instance_type` variable for budget runs at 4B. QLoRA on one H100 covers the entire ≤14B range this project could ever target; multi-GPU is not required for FuguTTX.

**Method:**
- **CPT pass:** QLoRA continued pretraining on the redistributable-clean corpus, 1–2 epochs, low learning rate, with general-domain replay data mixed in to prevent catastrophic forgetting.
- **SFT pass:** supervised fine-tuning from the CPT checkpoint on synthetic agentic traces (pf.conf debugging, pkg_add workflows, sysctl tuning, rcctl service management). Traces are generated by `ttx-synth` driving a **Qwen3-32B teacher served by vLLM on the same H100**, with tool calls constrained to the harness's JSON schemas at generation time, then judge-filtered for correctness and safety before entering the training set. Traces contain no thinking blocks and target ≤8K tokens, matching the inference context budget.
- **Execution:** training runs inside Axolotl's published CUDA Docker image on the instance (Scaleway's GPU OS image ships NVIDIA drivers and Docker with the NVIDIA container toolkit). All Axolotl YAML configs live in `packages/ttx-train/configs/` under version control; a run is `just train cpt` or `just train sft` against a provisioned instance. Checkpoints sync to Object Storage after every epoch, so destroying the instance never loses work.

**Cost estimates (order-of-magnitude, single H100-1-80G at ~€2.73/hour):**
- **CPT pass** (domain corpus, QLoRA, 1–2 epochs): ~10–20 GPU-hours → **~€28–55** per run.
- **Agentic SFT pass** (tens of thousands of traces): ~5–10 GPU-hours → **~€14–28** per run.
- **Trace generation** (Qwen3-32B teacher): ~5–10 GPU-hours per synthesis campaign → **~€14–28**.
- **Eval + iteration overhead:** budget 2–3× the "clean run" cost for sweeps and restarts.
- **Full TTX 1 program (CPT + SFT + several iterations):** on the order of **€200–500** of GPU time. Each promoted variant (§5) adds an SFT-dominated increment of roughly €50–150, since variants share the CPT checkpoint.

### 7. Scaleway infrastructure as code (OpenTofu)

Every Scaleway resource is declared in **OpenTofu** using the Scaleway provider. Nothing is created in the console. The point is not ceremony: per-minute GPU billing rewards fast create/destroy cycles, and IaC is what makes `destroy` safe, boring, and routine. The infrastructure code is ISC-licensed like the rest of the project tooling.

**Layout:**

```
infra/
├── modules/
│   ├── gpu-instance/     # scaleway_instance_server: GPU OS image, cloud-init, flexible IP
│   └── bucket/           # scaleway_object_bucket + access policy
├── persistent/           # long-lived stack: object storage, IAM — applied rarely
└── train/                # ephemeral stack: one GPU instance — up/down around each session
```

**Two stacks with two lifecycles:**
- **`infra/persistent`** — Object Storage buckets `ttx-corpus`, `ttx-checkpoints`, `ttx-artifacts`; an IAM application with an API key scoped to exactly those buckets for use by training instances. Applied rarely; changes reviewed like any code.
- **`infra/train`** — a single `scaleway_instance_server` (variable `instance_type`, default `H100-1-80G`, `L40S-1-48G` for budget runs) booting Scaleway's GPU OS image, with a flexible IP and a cloud-init script that pulls the Axolotl and vLLM images, installs the scoped API key, and syncs the corpus from Object Storage to scratch NVMe. The stack is applied at the start of a training session and destroyed at the end. There are no stop/hibernate half-states: **down means destroyed**, and since scratch NVMe is ephemeral anyway, the durability model makes destruction free of regret.

**Durability model:** Object Storage is the only durable layer. Corpus syncs down at boot; checkpoints sync up during training; release artifacts land in `ttx-artifacts`. `tofu destroy` can therefore never lose data — this invariant is what allows the aggressive teardown discipline that keeps costs low.

**State:** OpenTofu state lives in a dedicated Scaleway Object Storage bucket via the S3-compatible backend. That state bucket is the single resource not managed by OpenTofu; it is created once with `scw object bucket create` per the bootstrap runbook. FuguTTX is a single-operator project, so no distributed state locking is configured; this is documented and revisited if the team grows.

**Credentials:** `SCW_ACCESS_KEY`, `SCW_SECRET_KEY`, and `SCW_DEFAULT_PROJECT_ID` come from the operator's environment, never from the repository. The training instance receives only the bucket-scoped API key from the persistent stack, which is rotated after each training campaign.

**Task runner integration:**

```
just infra-plan train     # tofu plan  — review what a session will create
just infra-up train       # tofu apply — GPU billing starts here
just train cpt            # run the Axolotl CPT config on the instance
just train sft            # run the SFT config
just infra-down train     # tofu destroy — billing stops here
just infra-status         # list live resources, so nothing idles unnoticed
```

`just infra-up` prints the instance's hourly price on success, and `just infra-down` is a first-class step of the training runbook, not an afterthought.

**CI:** `tofu fmt -check` and `tofu validate` run on every push. CI holds no cloud credentials; `plan` and `apply` are always run by a human operator.

### 8. Quantization & inference plan for OpenBSD ≤16 GB RAM

- **Runtime:** the `misc/llama.cpp` port (`pkg_add llama.cpp`), CPU-only. The port is actively maintained (imported January 2025, tracking upstream releases) and builds across aarch64, alpha, amd64, arm, hppa, i386, mips64, mips64el, powerpc, powerpc64, riscv64, and sparc64. Dependencies: `devel/libggml`, `net/curl`, `cmake`, `ninja`. MIT-licensed upstream with `PERMIT_PACKAGE = Yes`.
- **Format:** GGUF. Three quants per release: **Q4_K_M is canonical** and validated by the full eval suite; **Q5_K_M** (for machines with headroom) and **Q3_K_M** (for the tightest boxes) are published with smoke validation only.
- **Fit in 16 GB:** 4B Q4_K_M ≈ 2.5–3 GB weights; 8B Q4_K_M ≈ 4.5–6 GB weights. Add roughly 0.5–2 GB KV cache at 4K–8K context and ~0.5–1 GB runtime overhead. Both fit with generous margin; anything 13B-class would fit weights-wise but be too slow CPU-only.
- **Performance:** CPU llama.cpp is memory-bandwidth-bound; consumer hardware yields roughly 10–15 tok/s for a 7B-class model. **No OpenBSD-specific tok/s benchmark has ever been published**, so FuguTTX measures this first-hand with `llama-bench` on target hardware and publishes the results as part of Phase 2.
- **Quantization execution:** `ttx-quant` wraps llama.cpp's `convert_hf_to_gguf.py` and `llama-quantize`; conversion is CPU-bound and runs on the operator's machine, no GPU required.
- **Development loop:** local iteration uses llama.cpp with Metal on Apple Silicon; the artifact that ships is the GGUF validated on OpenBSD CPU.
- **Release integrity:** every released GGUF ships with a `SHA256` manifest signed with **signify(1)**, matching how OpenBSD distributes sets and packages.

### 9. Harness (Perl)

**Language: Perl 5 from OpenBSD base, and nothing else.** The harness uses only modules available in base: `OpenBSD::Pledge(3p)` and `OpenBSD::Unveil(3p)` for sandboxing, `HTTP::Tiny` for the local llama-server API, `JSON::PP` for tool-call parsing. **Zero CPAN dependencies is a hard constraint, enforced by a CI check.** OpenBSD's own package tools are Perl written against base alone; the harness follows the same discipline. Nothing needs compiling, nothing needs a port dependency beyond llama.cpp itself.

**Architecture:** `llama-server` (from the `misc/llama.cpp` port) serves the TTX model over an OpenAI-compatible HTTP API on `127.0.0.1`; `ttx` drives a perceive → plan → act → observe loop against it. Together they form the TTX agent — the model proposes, the harness decides and executes. Tool calls are constrained at sampling time with llama-server's JSON-schema/grammar support, so model output is parseable by construction; `JSON::PP` validates anyway, and a malformed call gets one re-prompt, then the step aborts. The harness runs as a dedicated unprivileged user, `_ttx`.

**Tool set** (each a well-defined function with a JSON schema):
- **Read-only:** read config files under unveiled paths (`/etc/pf.conf`, `/etc/sysctl.conf`, `/etc/rc.conf.local`); run diagnostics — `pfctl -s rules|states|info`, `ifconfig`, `netstat`, `sysctl` (read), `pkg_info`, `rcctl get|check`, `dmesg`.
- **Gated mutations, dry-run first, always:**
  - Config edits write a candidate file, show the diff, validate (`pfctl -nf pf.conf.candidate`), and install only after explicit confirmation.
  - `pkg_add`/`pkg_delete` run with `-n` first; the real invocation requires confirmation.
  - `sysctl -w` records the previous value, requires confirmation, and offers rollback.
  - `rcctl enable|start|restart` requires confirmation.

**Safety design (first-class, not optional):**
- **pledge/unveil:** the harness pledges a minimal promise set (e.g. `stdio rpath wpath cpath inet proc exec` — `inet` only for the localhost API, `proc exec` only for the doas-gated tools) and unveils only what it needs: `/etc` read-only, `/usr/bin/doas` execute-only, its audit log write-only. Adoption of these mitigations across 19 OpenBSD releases is well studied and practical (Ruohonen, Sierszecki & Tiwari, arXiv:2607.03056).
- **doas, narrowly scoped:** privileged actions go through `doas` under per-command rules for the `_ttx` user rather than running the harness as root, e.g.:

  ```
  permit nopass _ttx as root cmd /sbin/pfctl args -nf /etc/pf.conf.candidate
  permit nopass _ttx as root cmd /usr/sbin/pkg_add args -n nginx
  ```

  Rules enumerate exact commands and arguments; anything outside the list fails closed.
- **Dry-run by default:** destructive actions require an explicit user confirmation after a successful dry run. There is no flag to disable this.
- **Auditability:** every prompt, tool call, executed command, and exit status is appended to `/var/log/ttx/audit.log`, opened append-only before privileges are dropped.

**Model fetching:** `ttx fetch` downloads GGUF artifacts by delegating to base `ftp(1)` (which speaks HTTPS) and verifies the signify signature against the pinned FuguTTX public key before the model is ever loaded. No TLS library dependency enters the harness.

**Packaging:** the harness ships as an OpenBSD port (`sysutils/ttx`) whose skeleton lives in-repo; it includes an `rc.d` script for running `llama-server` with the TTX model. Models are fetched separately via `ttx fetch` — weights do not ship inside the package.

### 10. Monorepo structure

This is a Python + Perl + HCL project. **uv workspaces** manage the Python packages (single lockfile, shared virtualenv, per-package `uv sync`); **`just`** is the polyglot task runner over all of it.

```
fuguttx/
├── justfile                     # top-level recipes: data, synth, train, eval, quant, infra, harness
├── CLAUDE.md                    # development-agent context: conventions, entrypoints, safety rules
├── pyproject.toml               # uv workspace root (virtual root, no app code)
├── uv.lock                      # single lockfile
├── .python-version              # 3.12
├── packages/                    # Python workspace members — all model-side work
│   ├── ttx-data/                # corpus scraping/extraction/cleaning
│   │   ├── fetch/               #   git-mirror sync (src/ports/www)
│   │   ├── extract/             #   mandoc render, HTML→text, code walk
│   │   └── clean/               #   dedup, license tagging, chunking
│   ├── ttx-synth/               # synthetic agentic trace generation (vLLM teacher client)
│   ├── ttx-train/               # training entrypoints
│   │   └── configs/             #   Axolotl YAML: cpt.yaml, sft.yaml, per-variant overlays
│   ├── ttx-eval/                # QA sets, agentic VM suite, judge client, scorecards
│   └── ttx-quant/               # GGUF conversion + quant sweep + signify manifest
├── harness/                     # the on-OpenBSD harness — Perl, base modules only
│   ├── bin/ttx                  #   entry point
│   ├── lib/TTX/                 #   Agent.pm, LLM.pm, Tools.pm, Sandbox.pm, Audit.pm
│   ├── t/                       #   prove(1) tests
│   └── port/                    #   OpenBSD port skeleton (Makefile, PLIST, DESCR, rc.d)
├── infra/                       # OpenTofu for Scaleway (modules/, persistent/, train/)
├── datasets/                    # dataset cards + manifests (not raw data)
├── models/                      # model cards + release manifests (GGUF via object storage/HF)
├── docs/                        # SPEC.md, corpus/licensing notes, runbooks/
│   └── runbooks/                #   bootstrap, training campaign, release
```

- **Task running:** `just data`, `just synth`, `just train cpt`, `just train sft`, `just eval`, `just quant`, `just infra-up train`, `just infra-down train`, `just harness-test`. A top-level `just check` aggregates every local lint/test/validate step and must pass before any commit — it is the same gate CI runs.
- **CI (GitHub Actions), no cloud credentials:** ruff + pytest for the Python packages; `perl -c` + `prove` + the no-CPAN-dependency check for the harness; `tofu fmt -check` + `tofu validate` for infra; Axolotl config validation. Heavy training stays manual on Scaleway.

### 11. Autonomous development

The monorepo is built to be planned, developed, and maintained by the development agents — Claude agents working autonomously, with humans reviewing outcomes rather than typing code. This section specifies what they need to operate — the environment, credentials, feedback loops, and boundaries — not how they coordinate. Throughout this section, "agent" means a development agent, never the TTX agent.

**The repository is the interface.** Everything an agent needs to act on already has a deterministic entrypoint: a `just` recipe for every pipeline stage, OpenTofu for every cloud resource, version-controlled Axolotl YAML for every training run, and runbooks in `docs/runbooks/` for every operational sequence. Autonomous development adds no parallel mechanisms — agents drive exactly the same commands humans do, so every action is reproducible and auditable regardless of who invoked it. If an agent needs a capability that has no recipe, the fix is to add the recipe, not to work around it.

**Runtime environment.** Agents need a persistent POSIX development environment with the full toolchain installed: git, `just`, uv (Python 3.12), OpenTofu, Perl with `prove`, qemu, llama.cpp, and the `scw` CLI. A bootable OpenBSD qemu image with snapshot support must be available in the environment — the Perl harness and the agentic eval suite can only be meaningfully exercised on OpenBSD. Long-running work (training campaigns, corpus builds, eval sweeps) requires the environment to outlive a single session or provide clean handoff between sessions: state that matters is committed to the repo, synced to Object Storage, or written to the runbook — never held only in an agent's context.

**Credentials, one scope per capability.** Each credential is provided through the environment or a secret store, never committed, and cut to the minimum the capability requires:

| Capability | Credential | Scope |
|---|---|---|
| Running the agents themselves | Anthropic API key (`ANTHROPIC_API_KEY`) | Project workspace |
| Infrastructure and training | Scaleway API key via a dedicated IAM application (separate from any human operator's) | Apply/destroy the `infra/` stacks, read/write the three project buckets, read consumption/billing so agents can watch their own spend; IAM administration excluded |
| Code review and CI | GitHub token | Push branches, open PRs, read checks; pushing to the default branch excluded — changes land only through reviewed PRs |
| Base models and datasets | Hugging Face token | Read for base-model downloads; write access withheld until release, which is a human step |
| Release signing | signify private key | **Never available to agents.** Signing is a human act, without exception |

**Spend controls.** Agents can start GPU instances, so cost discipline is enforced rather than assumed: a billing alert and documented monthly cap on the Scaleway project, `just infra-status` at the start and end of every working session, and `just infra-down` before any session ends with no training in flight. Spending beyond the per-campaign budget in the training runbook requires human approval.

**Feedback loops agents can run themselves.** Autonomous development is only as good as its verification, so every component defines done in a form a machine can check: `just check` reproduces the full CI gate locally; eval results are emitted as machine-readable scorecards, not prose; a smoke-train config (Qwen3-0.6B, tiny corpus slice) validates pipeline changes in minutes without a GPU campaign; harness changes run against disposable OpenBSD qemu snapshots where a destructive mistake costs a snapshot restore. Where an outcome cannot be verified mechanically — licensing judgment calls, release quality, benchmark publication — the runbook says so explicitly and the work routes to a human.

**Documentation is written for agents.** This SPEC, the runbooks, and the corpus/licensing notes are the agents' source of truth; keeping them current is part of every change, not an afterthought. The root `CLAUDE.md` carries the per-session context: repository conventions, entrypoints, and the standing safety rules — never leave a GPU instance running unattended, never move eval/RAG-corpus material into a training manifest, never sign or publish artifacts.

**Human decision points.** Agents plan, implement, train, evaluate, and iterate on their own. Four decisions stay human:
1. **Merging.** Agents open pull requests; a human reviews and merges. A green `just check` is necessary, never sufficient.
2. **Releasing.** Signing (signify) and publishing weights, datasets, and the harness port.
3. **Spending** beyond the documented per-campaign budget.
4. **Licensing lanes.** Any change to what enters the training corpus versus the eval/RAG corpus.

The symmetry is deliberate: FuguTTX ships the TTX agent bounded by pledge/unveil, doas, and dry-run gates, and the development agents that build it operate under the same philosophy — least privilege by construction, explicit gates before irreversible actions, and an append-only audit trail (git history, CI logs, OpenTofu state).

### 12. Evaluation plan

- **Domain knowledge (perplexity/NLL)** on a held-out slice of the clean corpus, to confirm CPT actually injected OpenBSD knowledge; an MMLU-style general benchmark runs in parallel as a guardrail against catastrophic forgetting.
- **OpenBSD-specific QA eval set:** hand-curated Q&A drawn from man pages and FAQ (e.g. "what does `pfctl -sr` show?", "how do you enable IP forwarding via sysctl?"), graded by exact-match/keyword plus an LLM judge — the same Qwen3-32B deployment that generates training traces.
- **Agentic task suite (SWE-bench-style, adapted to sysadmin):** scripted scenarios in disposable OpenBSD VMs run under qemu with snapshot-restore between scenarios — "block inbound SSH except from 10.0.0.0/8 in pf.conf", "install and enable nginx", "diagnose why pf is dropping a connection" — scored on task completion *and* safety (did it dry-run first? did it avoid destructive mistakes?). qemu keeps the suite portable across the development machine and CI.
- **Tool-call correctness:** JSON-schema validity and hallucinated-flag rate, measured end-to-end through the harness. Synthetic-data research is the warning here: naive synthetic tool calls have shown malformed-output rates approaching 30%, which is why generation is schema-constrained and judge-filtered.
- **Safety red-team:** adversarial prompts attempting to trigger `pkg_delete -a`, `rm`, or a firewall lockout; every one must hit the dry-run/confirm gates. Any escape is a release blocker.

### 13. Licensing & release strategy

- **Weights:** released under **Apache 2.0**, inherited cleanly from the Apache-2.0 base model (§4). Any base — for TTX 1 or for any variant — that would force a restrictive derivative license is excluded by policy.
- **Code:** everything in the repository — Python packages, Perl harness, OpenTofu — under **ISC**, OpenBSD's preferred license for new code (`/usr/share/misc/license.template`, functionally equivalent to two-clause BSD).
- **Datasets:** the clean corpus derives from ISC/BSD source, mandoc (ISC) man pages, and the BSD-licensed FAQ/www — all redistributable with attribution/notice, and documented in published **dataset cards** covering the source, filtering, and license class of every component. Mailing-list archives and undeadly.org are copyright their individual authors: they live exclusively in the eval/RAG corpus, never enter training data, and their raw text is never redistributed. The pipeline's license tags enforce the lane mechanically.
- **Model cards** document base model, corpus composition, training method, eval results, and known limitations for every release.
- **Release integrity:** GGUF artifacts, manifests, and dataset cards are published with signify(1) signatures under the pinned FuguTTX key.

### 14. Roadmap / milestones

1. **Phase 0 — Bootstrap.** Monorepo scaffold, CI, OpenTofu persistent stack, train-stack round-trip, runbooks, and the autonomous-development environment (toolchain, scoped credentials, OpenBSD qemu image, `CLAUDE.md`). *Exit:* CI green; `just infra-up train` → `just infra-down train` verified end-to-end; a development agent can complete a full plan → implement → `just check` → PR cycle unassisted.
2. **Phase 1 — Corpus.** Mirror sync, extraction pipeline, both corpora with license tagging. *Exit:* reproducible `just data` producing tagged, deduped, license-classed text; corpus/licensing notes published.
3. **Phase 2 — Baseline eval.** Build the OpenBSD QA + agentic eval sets; benchmark Qwen3-4B zero-shot on OpenBSD tasks; measure CPU tok/s on real OpenBSD hardware with `llama-bench`. *Exit:* baseline scorecard + the first published OpenBSD CPU inference benchmark.
4. **Phase 3 — Continued pretraining.** QLoRA CPT on the clean corpus (H100-1-80G) with replay + low LR. *Exit:* CPT checkpoint beating base on domain perplexity without MMLU regression.
5. **Phase 4 — SFT / agentic tuning.** Generate and judge-filter synthetic tool-use traces with the Qwen3-32B teacher; SFT from the CPT checkpoint. *Exit:* agentic eval pass-rate threshold met and tool-call validity high; escalation decision (4B vs 8B) made here.
6. **Phase 5 — Quantization & export.** GGUF Q4_K_M (canonical) / Q5_K_M / Q3_K_M; validate quality retention; sign artifacts. *Exit:* signed GGUF artifacts + quant quality report.
7. **Phase 6 — Harness integration.** The Perl harness complete with pledge/unveil, doas policies, dry-run gates, audit log; port skeleton builds. *Exit:* the end-to-end TTX agent passes the eval suite in a VM safely.
8. **Phase 7 — TTX 1 release.** Weights (Apache 2.0), model card, harness port, docs, benchmark publication.
9. **Phase 8 — Specialist variants.** Build the candidate personas' eval suites, run TTX 1 against them, and apply the promotion rule (§5); train and release the overlays that earn it. *Exit:* a recorded promotion decision for every candidate; promoted variants released with the same discipline as TTX 1.

### 16. Risks

- **Hallucination on destructive commands (highest risk):** a 4B model may confidently emit a wrong `pfctl`/`pkg_delete`/`sysctl` command. Mitigated with mandatory dry-run/confirm gates, per-command doas rules, pledge/unveil, and the safety red-team eval — unattended execution of destructive actions is never allowed, by design rather than by policy.
- **Corpus staleness vs `-current`:** OpenBSD moves fast, so a model trained on a snapshot drifts from `-current`. Mitigated with periodic re-training against fresh mirrors and local RAG over live man pages/FAQ for facts that change frequently.
- **Evaluation difficulty:** sysadmin agentic tasks are hard to grade automatically; the qemu VM suite is real engineering effort and a project dependency, not an afterthought — it is scheduled as its own phase.
- **Synthetic data quality:** naive synthetic agentic traces have high malformed-tool-call rates. Mitigated by schema-constrained generation against the harness's actual tool schemas, a strong teacher (Qwen3-32B), and aggressive judge-filtering; residual quality risk is measured by the tool-call validity eval.
- **Licensing lane discipline:** author-copyrighted material (lists, undeadly.org) must stay in the eval/RAG lane. Mitigated mechanically: license tags are applied at extraction and checked before any training manifest is built.
- **Pricing/availability drift:** Scaleway prices and GPU stock vary by region and over time; the console is verified before each campaign. Exposure is bounded structurally by per-minute billing and the create/destroy lifecycle — an idle GPU can only cost money while `just infra-status` shows it exists.
- **Development-agent blast radius:** a development agent holding cloud credentials can leave instances running, mangle infrastructure, or land a bad change. Mitigated structurally, not by trust: per-capability credential scopes with IAM administration and the signify key withheld, spend caps and billing alerts, PR-only merges with human review, Object Storage as the sole durable layer (so `tofu destroy` is always safe), and the same audit trail humans leave — git history, CI logs, OpenTofu state.
